## Slide 1｜Prompt Injection 是什麼？

**投影片文字**

- Prompt Injection（提示注入）：把指令放進模型正在處理的輸入或資料。
- 如果模型把它當成應遵循的指令，可能偏離原本任務。
- 例：郵件助理整理郵件時，郵件內容藏有另一段指令。

**講者稿**  
先想像一個郵件助理：我們請它整理郵件，但它讀到的郵件裡也出現一段命令。Prompt Injection 指的就是這類情況：指令被放在模型正在處理的輸入或資料中；如果模型把它當成要聽從的指令，就可能離開原本任務。這個郵件例子來自 AgentDojo 的測試情境，不表示所有郵件助理都會發生同樣結果。

**建議視覺**  
簡單流程圖：`整理郵件的任務` ＋ `含指令的郵件資料` → `模型可能偏離任務`。

**頁底來源**  
S2，PDF pp. 1–2（Figure 1）；S6，PDF pp. 1–2。

**限制／注意事項**  
將郵件例子標為測試情境；不同來源的定義焦點不完全相同，不額外提出統一定義。

## Slide 2｜為什麼 LLM 容易受到影響？

**投影片文字**

- 模型可能同時收到「要遵循的指令」和「要處理的資料」。
- 常見輸入形式沒有可靠邊界，讓模型在所有情況下都正確分辨兩者。
- 資料中的命令式文字可能被當成新指令。

**講者稿**  
模型的輸入可能同時包含任務指令和資料。例如，任務是摘要郵件，而郵件正文是要處理的資料。來源指出，常見輸入形式未必能讓模型可靠地分辨每段文字是指令還是資料。因此，資料裡看起來像命令的文字可能被誤當成新指令。這裡說的是來源共同描述的辨識問題；我們不再推測模型內部如何運作。

**建議視覺**  
兩欄「任務指令」與「待處理資料」在模型輸入處匯合，突出兩種文字可能難以區分。

**頁底來源**  
S2，PDF p. 1；S5，PDF p. 1；S6，PDF pp. 1–2。

**限制／注意事項**  
不把共同問題描述延伸成未由 Evidence Cards 支持的模型內部機制。

## Slide 3｜Direct 與 Indirect Prompt Injection

**投影片文字**

| Direct | Indirect |
|---|---|
| 指令由主要使用者透過 query／input 直接送入 | 指令藏在模型讀取或取回的外部資料中 |
| 使用者直接輸入企圖蓋過原任務的命令 | 使用者可能沒有提供或看見該指令 |

**講者稿**  
兩者最容易辨認的差別，是指令從哪裡進入。Direct Prompt Injection 的指令由主要使用者直接送入；Indirect Prompt Injection 則藏在模型受命讀取或取回的外部資料中。使用者可能根本沒有看見那段外部指令。需要留意，不同來源對 Direct 和相關術語的分類方式並不完全一致，因此這個對照是入門整理，不代表所有來源採用完全相同的分類。

**建議視覺**  
左右對照路徑：`使用者輸入 → 模型` 與 `外部資料 → 模型`；用深藍標示入口，避免把兩條路徑畫成相同。

**頁底來源**  
S1，PDF p. 3（含註 1）；S2，PDF p. 2；S3，PDF pp. 1–3；S5，PDF p. 2。

**限制／注意事項**  
保留 S1 轉述 NIST 時的 Direct Prompt Injection／Direct Prompting Attack 用語差異，以及 S5 對 User Prompt Injection Attack／jailbreaking 的說法；不要合併成唯一分類。

## Slide 4｜Prompt Injection 可能帶來哪些安全風險？

**投影片文字**

- **Availability：** 可用性受損
- **Integrity：** 輸出或系統完整性受影響
- **Privacy：** 隱私或資料受損
- **Misuse：** 促成不當使用
- 論文另討論或示範資料外洩、工具操作、遠端影響、錯誤摘要等情況。

**講者稿**  
Wiki 整理的 NIST 目標分類有四類：Availability、Integrity、Privacy 和 Misuse。初學者可以先把它們理解為服務可用性、結果完整性、資料隱私，以及不當使用等面向。其他論文還討論或示範了工具操作、資料外洩或錯誤摘要等情況。不過，這些分類和例子不是同一種分類系統，也不是每一項都代表普遍發生的實際事件。

**建議視覺**  
四格風險分類圖；旁邊用小型「論文測試／示例」框列一個例子，與分類區分開。

**頁底來源**  
S1，PDF p. 3；S2，PDF pp. 1–2；S3，PDF pp. 1–3、9。

**限制／注意事項**  
NIST 目標分類與 Greshake et al. 威脅類別分開標示。郵件外洩是 AgentDojo benchmark 情境；錯誤摘要是論文示例，不說成普遍實際事件。

## Slide 5｜防禦方向一：分清指令與資料

**投影片文字**

- **Structured Queries／StruQ：** 把 prompt 與 data 分開編碼。
- **Spotlighting：** 轉換外部輸入，提供資料來源線索。
- Spotlighting 的做法：Delimiting、Datamarking、Encoding。

**講者稿**  
一類方法會嘗試讓指令和資料更容易區分。Structured Queries 的 StruQ 作法，是把 prompt 和 data 分開編碼，並以 structured instruction tuning 訓練模型遵從 prompt 部分。另一個方向是 Spotlighting，透過轉換外部輸入來提供資料來源線索；其中包括 Delimiting、Datamarking 和 Encoding。這些是不同做法，不能只因目的相近就當成相同方法。

**建議視覺**  
防禦分類圖，分成「結構化區分」與「Spotlighting 輸入轉換」兩支；下方列出三種 Spotlighting 方法名稱。

**頁底來源**  
S6，PDF pp. 7–8；S5，PDF pp. 2–3。

**限制／注意事項**  
StruQ 與 Spotlighting 的適用情境和實驗設定不同，不暗示兩者可互換或在所有應用中有效。

## Slide 6｜防禦方向二：限制或檢查 Agent 工具流程

**投影片文字**

- **Tool filtering：** 事先只開放預計完成任務所需的工具。
- **Prompt injection detector：** 檢查工具輸出；偵測到注入時中止代理人。
- **Prompt sandwiching：** 工具呼叫後重申使用者任務指令。

**講者稿**  
AgentDojo 評估了幾種放在代理人流程中的方法。Tool filtering 是在讀取不可信資料前先選定需要的工具。Detector 會檢查工具輸出，若判定有注入就中止代理人。Prompt sandwiching 則是在工具呼叫後重新附上使用者原本的任務指令。這些方法來自 AgentDojo 的測試，不代表所有 Agent 都會有相同結果。

**建議視覺**  
簡化工具流程圖：在「選工具」「檢查工具輸出」「工具呼叫後」三處分別標示三種方法。

**頁底來源**  
S2，PDF pp. 8–9。

**限制／注意事項**  
Least Privilege 在目前 Evidence Cards 中資料不足；不要把 tool filtering 直接稱為 Least Privilege。

## Slide 7｜防禦方法各有適用範圍

**投影片文字**

- Delimiting：攻擊者仿造界定符可能造成混淆。
- 靜態 Datamarking：只標記空格可能漏掉無空格文字。
- Encoding：較弱模型可能解碼或完成下游任務時出錯。
- Tool filtering、detector 與 StruQ 也各有適用條件或限制。

**講者稿**  
這一頁只看各種方法本身的適用條件與質性限制，不比較實驗分數。Spotlighting 的來源指出，Delimiting 可能受仿造界定符影響；只替換空格的靜態 Datamarking 可能漏掉無空格的攻擊文字；Encoding 可能對較弱模型造成解碼或下游任務困難。Tool filtering 取決於能否事先選工具；detector 可能誤判正常內容；StruQ 也有其適用範圍。下一頁再看實驗結果如何受測試設定限制。

**建議視覺**  
簡單比較表：「方法／適用條件／已知限制」，只保留本頁列出的代表性限制。

**頁底來源**  
S5，PDF pp. 4–6；S2，PDF p. 9；S6，PDF pp. 10、14。

**限制／注意事項**  
聚焦於方法的適用條件與質性限制，不在本頁列出 ASR、utility 或跨研究數值。實驗數值與設定集中於下一頁說明。

## Slide 9｜目前能否說「已經完全防禦」？

**投影片文字**

- 目前來源指出多種防禦方法的具體限制與部分未解問題。
- 但不足以證明所有 Prompt Injection 都無法防禦。
- 也不足以證明已有適用所有系統的完整解法。
- **結論：資料不足／尚無定論。**

**講者稿**  
我們可以從目前整理的研究中看到，不同方法各有適用條件，也有來源明確指出的限制。但這些研究不足以回答所有模型、任務和攻擊情境是否都能防住。結論應保留為「資料不足／尚無定論」：不能說已經證明完全防禦不可能，也不能說已經有一種能適用所有系統的完整解法。

**建議視覺**  
左右兩區：「目前知道：特定方法有具體限制」與「仍未確定：能否完全防禦所有情境」，中間以「資料不足／尚無定論」收束。

**頁底來源**  
S2，PDF pp. 9、20；S5，PDF pp. 4–6；S6，PDF pp. 10、14。

**限制／注意事項**  
不將「尚無足夠證據」改寫成「已證明不可能」或「已完全防禦」；不超出 Evidence Cards 推論。
