## 頁面大綱

### Slide 1｜Prompt Injection 是什麼？

- **教學目的：** 建立全篇共用的基本概念。
- **主要重點：**
  1. 攻擊者把指令放進模型正在處理的輸入或資料。
  2. 若模型把它當成應遵循的指令，可能偏離原任務。
  3. 郵件助理例子是 AgentDojo 的測試情境。
- **對應 Evidence Card ID：** EC-01
- **建議視覺呈現方式：** 簡單流程圖：「原任務指令＋待處理資料（含指令）→ 模型可能偏離任務」；避免呈現卡片以外的攻擊細節。
- **本頁需要保留的限制或注意事項：** 郵件案例屬論文測試情境，不代表所有郵件助理都會如此；來源描述焦點不同，不應擴張成更強的統一定義。

### Slide 2｜為什麼 LLM 容易受到影響？

- **教學目的：** 說明指令與資料在輸入中的辨識問題。
- **主要重點：**
  1. 模型可能同時收到「要遵循的指令」和「要閱讀或處理的資料」。
  2. 常見輸入形式沒有可靠邊界能讓模型在所有情況下都正確分辨兩者。
  3. 資料中的命令式文字可能被當成新指令。
- **對應 Evidence Card ID：** EC-02
- **建議視覺呈現方式：** 兩欄輸入圖：「任務指令」與「待處理資料」，在模型入口合流時用深藍標出辨識難點。
- **本頁需要保留的限制或注意事項：** 只呈現 Wiki 的共同問題描述；不新增模型內部如何運作的研究結論。

### Slide 3｜Direct 與 Indirect Prompt Injection

- **教學目的：** 讓初學者辨認攻擊指令進入模型的不同途徑。
- **主要重點：**
  1. Direct：攻擊指令由主要使用者透過 query／input 直接送入。
  2. Indirect：指令藏在模型受命讀取或取回的外部資料中，使用者可能沒有提供或看見。
  3. 兩者差異重點是指令來源與進入途徑。
- **對應 Evidence Card ID：** EC-03、EC-04
- **建議視覺呈現方式：** Direct vs Indirect 雙欄對照：使用者輸入 → 模型；外部資料 → 模型。以來源位置作主要視覺差別。
- **本頁需要保留的限制或注意事項：** 分類用語不是所有來源都完全一致；S1 轉述 NIST 的用語範圍差異，S5 對 User Prompt Injection Attack／jailbreaking 的稱法，請在頁底註記或講者備註並列，不合成唯一分類。

### Slide 4｜Prompt Injection 可能帶來哪些安全風險？

- **教學目的：** 以清楚分類呈現來源討論的風險範圍。
- **主要重點：**
  1. S1 轉述的 NIST 分類：Availability、Integrity、Privacy、Misuse。
  2. Wiki 另整理了資料外洩、工具操作、遠端影響及錯誤摘要等論文討論／示例。
  3. 風險與應用可讀取的資料、可呼叫工具及輸出處理方式有關。
- **對應 Evidence Card ID：** EC-05
- **建議視覺呈現方式：** 四格風險分類圖；另用一個較小的「論文示例」區塊呈現郵件外洩或錯誤摘要，不把示例混成普遍事件。
- **本頁需要保留的限制或注意事項：** NIST 目標分類與 Greshake et al. 威脅類別的目的和粒度不同，分開標示。測試或論文示範不可稱為普遍實際事件。

### Slide 5｜防禦方向一：分清指令與資料

- **教學目的：** 介紹透過輸入設計提供區分線索的兩種方法。
- **主要重點：**
  1. Structured Queries／StruQ：把 prompt 與 data 分開編碼，並以 structured instruction tuning 訓練模型遵從 prompt 部分。
  2. Spotlighting：轉換外部輸入，提供資料來源線索。
  3. Spotlighting 包含 Delimiting、Datamarking、Encoding 三種做法。
- **對應 Evidence Card ID：** EC-06
- **建議視覺呈現方式：** 防禦分類圖，分成「結構化分隔」和「輸入標記／轉換」兩支；每項僅放一行概念。
- **本頁需要保留的限制或注意事項：** StruQ 適用於特定程式化應用；Spotlighting 的效果依模型、任務與設定而異。不要讓這頁暗示方法可互換或有普遍保證。

### Slide 6｜防禦方向二：限制或檢查 Agent 工具流程

- **教學目的：** 認識 AgentDojo 評估的三種流程層級方法。
- **主要重點：**
  1. Tool filtering：預先只開放預計完成任務所需工具。
  2. Prompt injection detector：檢查工具輸出，偵測到注入時中止代理人。
  3. Prompt sandwiching：每次工具呼叫後重申使用者任務指令。
- **對應 Evidence Card ID：** EC-06、EC-07
- **建議視覺呈現方式：** 簡化 Agent 流程圖，在「選工具」「讀取工具輸出」「繼續執行」三個位置標記相應方法。
- **本頁需要保留的限制或注意事項：** 這些方法是在 AgentDojo 中測試的流程，不代表所有 Agent 的結果。`Least Privilege` 在 Wiki 中資料不足，不能把它直接等同 tool filtering。

### Slide 7｜防禦方法各有適用範圍

- **教學目的：** 避免把單一防禦方式理解為萬用解法。
- **主要重點：**
  1. Delimiting 可能受仿造界定符影響；靜態 Datamarking 可能漏掉無空格文字。
  2. Encoding 可能對較弱模型的解碼與下游任務造成困難。
  3. Tool filtering 受工具是否能事先規劃、以及正常任務和攻擊是否共用工具限制。
  4. Detector 可能出現 false positives；StruQ 也有特定適用範圍。
- **對應 Evidence Card ID：** EC-07
- **建議視覺呈現方式：** 簡單比較表：「方法／適用條件／已知限制」，只選以上代表性限制，避免塞入所有細節。
- **本頁需要保留的限制或注意事項：** 限制須對應原方法及來源情境；AgentDojo 的文字敘述約 7.5% 與 Table 5 的 6.84% 是同篇論文不同位置的數值，若簡報引用必須並列，不合成單一數字。

### Slide 8｜防禦效果也要看測試設定

- **教學目的：** 建立閱讀實驗數字時的證據邊界意識。
- **主要重點：**
  1. AgentDojo 的 targeted ASR 與 benign utility 來自該 benchmark 的特定模型與配置。
  2. Detector 的測試呈現攻擊成功率與正常任務效用之間的取捨。
  3. Spotlighting、AgentDojo 與 StruQ 的模型、任務和方法不同，結果不可直接合併比較。
- **對應 Evidence Card ID：** EC-06、EC-07
- **建議視覺呈現方式：** 以「模型／任務／防禦／觀察結果」四欄小型比較表；若放 AgentDojo tool-filter 數值，將約 7.5% 和 6.84% 並列標註各自位置。
- **本頁需要保留的限制或注意事項：** 所有數值都限定在其論文所述模型、任務與 benchmark；不得推廣到所有 LLM、RAG 或 Agent。若版面過於擁擠，可不放數字，只保留情境限制。

### Slide 9｜目前能否說「已經完全防禦」？

- **教學目的：** 以謹慎且符合證據的結論收束全篇。
- **主要重點：**
  1. Wiki 所整理來源呈現多種具體方法限制及部分未解問題。
  2. 這些材料不足以證明所有 Prompt Injection 都不可能防禦，也不足以證明存在適用所有系統的完整解法。
  3. 結論狀態：資料不足／尚無定論。
- **對應 Evidence Card ID：** EC-07、EC-08
- **建議視覺呈現方式：** 以「已知：特定方法在特定情境有具體限制」與「尚未確定：能否完全防禦所有情境」兩區收尾。
- **本頁需要保留的限制或注意事項：** 不可改寫成「已證明完全防禦不可能」或「現在已有完整防禦」；保留資料不足／尚無定論，不做超出 Evidence Cards 的推論。
